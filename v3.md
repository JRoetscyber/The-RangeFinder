# RangeFinder — v3: Production / Open-Source-Ready

## What's new vs v2
1. **Config file (YAML/JSON)** — stop re-typing long CLI invocations; define
   a target profile once and reuse it.
2. **Pluggable ID generators** — sequential ints, wordlists, UUID sweeps
   (low-value against random v4, but useful against v1/v7 time-based UUIDs),
   and hashid-style/base62 patterns.
3. **Multi-endpoint sweeps** — one config can define several endpoint
   templates (e.g. `/api/users/{ID}`, `/api/orders/{ID}`, `/api/invoices/{ID}`)
   and run them all, since IDOR often clusters across an API's resource types.
4. **Proxy support** — route traffic through a local proxy (Burp/ZAP) so you
   can manually inspect anything interesting as it happens.
5. **Structured reporting** — JSON and CSV output with severity tagging, so
   results are easy to triage or paste into a report.
6. **Clean modular architecture** — split into packages so it's actually
   pleasant for other contributors to extend once you open it up.

## Pluggable ID generator (internal/generator/generator.go)

```go
package generator

import (
	"bufio"
	"fmt"
	"os"
)

// Generator produces a stream of ID strings to substitute into a URL template.
type Generator interface {
	Generate() <-chan string
}

// Sequential produces string(int) for a numeric range.
type Sequential struct {
	Start, End int
}

func (s Sequential) Generate() <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for i := s.Start; i <= s.End; i++ {
			out <- fmt.Sprintf("%d", i)
		}
	}()
	return out
}

// Wordlist streams lines from a file, so memory use stays flat on huge lists.
type Wordlist struct {
	Path string
}

func (w Wordlist) Generate() <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		f, err := os.Open(w.Path)
		if err != nil {
			return
		}
		defer f.Close()
		scanner := bufio.NewScanner(f)
		for scanner.Scan() {
			out <- scanner.Text()
		}
	}()
	return out
}

// Base62 produces zero-padded base62 strings across a numeric range —
// useful against short account codes that aren't plain decimal.
type Base62 struct {
	Start, End int
	Width      int
}

const base62Alphabet = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

func toBase62(n, width int) string {
	if n == 0 {
		return pad("0", width)
	}
	s := ""
	for n > 0 {
		s = string(base62Alphabet[n%62]) + s
		n /= 62
	}
	return pad(s, width)
}

func pad(s string, width int) string {
	for len(s) < width {
		s = "0" + s
	}
	return s
}

func (b Base62) Generate() <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for i := b.Start; i <= b.End; i++ {
			out <- toBase62(i, b.Width)
		}
	}()
	return out
}
```

Adding UUID-sweep support: for v1/v7 (time-ordered) UUIDs, generate
candidates by varying the timestamp component across a plausible window and
randomizing the rest per RFC structure. For pure v4 (fully random) UUIDs,
brute-force enumeration isn't practically feasible — don't build a generator
that implies it is; this is where the tool's docs should say "not applicable."

## Multi-endpoint runner sketch (cmd/rangefinder/main.go — shape only)

```go
for _, target := range cfg.Targets {
	gen := generatorFor(target)        // picks Sequential/Wordlist/Base62
	baseline := fetchBaseline(target, cfg)
	runSweep(target, gen, baseline, cfg, reportSink)
}
reportSink.Flush() // writes results.json + results.csv
```

Keep each target's results tagged with `target.Name` in the report so a
multi-endpoint run's output is easy to filter.

## Reporting (internal/report/report.go — shape)

```go
type Hit struct {
	Target     string  `json:"target"`
	ID         string  `json:"id"`
	StatusCode int     `json:"status_code"`
	Similarity float64 `json:"similarity"`
	URL        string  `json:"url"`
	Severity   string  `json:"severity"` // heuristic: e.g. "review" vs "likely"
}
```

Tag severity heuristically: status 200 + similarity far below threshold +
non-empty body → `likely`; anything borderline → `review`. This keeps your
triage queue honest instead of drowning you in noise once wordlists get large.

## Open-sourcing checklist
- **README with a clear scope/authorization disclaimer** up front — state
  plainly that this is for use only against assets you're authorized to test
  (bug bounty scope, pentest engagement, your own infra), and that misuse is
  the user's responsibility, not the tool's.
- **Sane defaults that are slow, not fast** — ship with a conservative
  default `rps` so a copy-pasted quickstart command doesn't hammer someone's
  production API.
- **No baked-in target lists or real program data** in example configs —
  keep examples pointed at `localhost` or placeholder domains.
- **Contribution guide** — since the generator/diff logic is the most
  extensible part, document the `Generator` interface clearly so others can
  add new ID-space strategies (e.g. hashid-aware generation) without
  touching the core fetch loop.
- **License** — MIT or Apache-2.0 are the norm for this category of tool.

## What v3 still doesn't do (and probably shouldn't, in scope)
- Doesn't attempt to bypass auth, WAFs, or rate limits beyond polite backoff
- Doesn't auto-exploit anything it finds (no automatic data exfiltration) —
  it reports candidate IDORs for a human to verify and report responsibly
- Doesn't brute-force cryptographically random identifiers (v4 UUIDs,
  long random tokens) — that's not enumeration, that's just not feasible,
  and the tool shouldn't pretend otherwise
